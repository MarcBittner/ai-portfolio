## Notes

**What works well.** The codebase is compact, well-documented, and the module boundaries are clean (`classify → policy → controls → scan → api`). The LLM routing chain has a proper deterministic offline fallback so the whole stack runs with zero keys. Tests have good coverage of the observable contract (classification classes, DDL shape, gate pass/fail, control frameworks).

**Finding 1 detail (silent false-negative).** `classify_column` at the free-text branch calls `llm.complete(…, offline=_free_text_offline)`. The offline function always returns valid JSON, so the offline path never triggers the parse failure. The risk materialises only when a real LLM provider is configured. The provider's raw response is passed to `_parse_phi`; if the model inserts preamble before the JSON object and the markdown-fence stripping (`split('```')[1]`) fails (e.g. the model uses single backticks or no fences), the `json.loads` raises, the `except Exception` returns `[]`, and CLAIM_NOTE is classified `non_sensitive`. The CI gate then passes on a column that contains PHI — exactly the outcome the tool is designed to prevent.

**Finding 2 detail (race on `_CON`).** In CPython the GIL makes the assignment `_CON = connect()` itself atomic, so data is never corrupted, but the check-then-assign window means two threads can both call `connect()` and the first DuckDB in-memory database is abandoned without being closed. More practically, `reset()` replaces `_CON` without waiting for any in-flight `execute()` call on the old connection to complete; DuckDB's in-memory connection is not re-entrant.

**Finding 5 detail (REPORT path).** `parents[2]` from `src/maskline/evaluate.py` reaches the project root when running from source, which is the intent. The same expression from a site-packages path resolves three levels up from the installed `.py` file, almost certainly a system directory. A simple `Path.cwd() / 'eval-report.md'` default is safer and more predictable.
