## Notes

**Strengths**

- The deterministic rule engine is correct: direction scoping, redaction of matched secrets/PII, and the score → verdict mapping are all consistent across `scan.py` and the API layer.
- Secret non-leakage is tested at multiple levels (unit `test_scan.py`, API `test_api.py`, security suite `test_security.py`), including planting canary API keys in env vars and asserting they never appear in any response body.
- The `/providers` endpoint exposes only booleans, never key material — this is correctly verified in `test_security.py`.
- The mock provider acts as a safe terminal fallback: `complete()` never raises, and `complete_json()` returns `None` (no verdict) on mock, keeping the deterministic rules as the sole signal.
- The Dockerfile is non-root (`uid 1001`) and uses a slim base; no dev/test dependencies in the production image.

**Minor observations**

- The `client_classification` trust model is documented inline (browser→host bridge for reaching `localhost:11434` from a cloud server). For the demo use case this is intentional, but API consumers who expose promptguard to untrusted callers should be made aware in the README that this field bypasses the LLM layer.
- `run.sh` smoke test writes logs to `${TMPDIR:-/tmp}/${PROJECT}-smoke.log`, which is world-writable on shared systems. Non-critical for a dev script but worth `/tmp`-isolation on CI.
- The `esc()` function is defined twice in `index.html` (line 487 and again locally in the app launcher closure at line 793). The duplication is intentional for scope isolation but could be consolidated.
