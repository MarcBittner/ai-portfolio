# Code Review — trueline

**Health:** fair — well-architected for a demo app (deterministic money logic, clean multi-tenancy, solid test coverage of critical paths), but has two resource-exhaustion risks that should be closed before any real traffic and several correctness gaps in rollup accounting.

## Notes

**Architecture strengths:** The separation of LLM extraction (read-only) from deterministic reconciliation is correct and well-enforced. Money decisions are never delegated to the model. Multi-tenancy is consistently scoped through `orgId` from Clerk JWTs, and the org-isolation guard (`inv.orgId !== orgId`) is applied on every mutation before any write. The benchmark/eval pipeline gives regression visibility. Tests cover the money-critical edge cases (cross-SKU borrowing, rounding boundaries) that most projects leave uncovered.

**Two findings to prioritize:** Finding #2 (unauthenticated benchmark runs LLM calls) and Finding #1 (unbounded rawText) are the most practically dangerous in a live deployment with real API keys. Both are one-line fixes. Finding #3 (stale invoice rollups after correction) is the most user-visible correctness gap.

**Finding #4 and #5 (N+1 / unbounded collect):** These are acceptable for a demo app with a handful of invoices per tenant, but will degrade noticeably at ~50+ invoices. The rollup-on-write pattern already in use for `recoverableUsd`/`claimedTotal` is the right model to extend.
